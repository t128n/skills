# Implementation Specification: `@t128n/skills` Skills Pack v2

## Objective

Rebuild the Skills Pack implementation as a reliable, reproducible, standards-compliant skills distribution system.

Preserve the existing architecture where it works. Improve dependency resolution, integrity verification, deployment, testing, and developer experience.

**Engineering philosophy:** Simple, deterministic, explicit, and maintainable. Prefer established technologies and standards. Do not introduce infrastructure or abstractions without concrete justification.

## 1. Standards and technical references

Research and use the latest applicable versions of:

- [Agent Skills specification](https://agentskills.io/specification) — skill directories, frontmatter, naming, and resources.
- [Agent Skills Discovery v0.2.0](https://github.com/cloudflare/agent-skills-discovery-rfc) — public discovery index, artifact URLs, content digests, and archives.
- [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12) — configuration and lockfile schemas.
- [skills CLI](https://github.com/vercel-labs/skills) — discovery and installation compatibility.
- [GitHub Pages Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages) — static deployment.

Distinguish requirements from the external specifications from our own implementation policies.

Do not invent proprietary extensions to the published discovery format.

For v2, target the existing v0.2.0 discovery format unless research reveals a newer, stable, compatible version that has been adopted by the target CLI.

## 3. Public discovery format

The generated index must follow Agent Skills Discovery v0.2.0 exactly.

Example:

```json
{
  "$schema": "https://schemas.agentskills.io/discovery/0.2.0/schema.json",
  "skills": [
    {
      "name": "find-skills",
      "type": "skill-md",
      "description": "Discover and install agent skills.",
      "url": "find-skills/SKILL.md",
      "digest": "sha256:<64-lowercase-hex-characters>"
    },
    {
      "name": "engineering-principles",
      "type": "archive",
      "description": "Review stateful and I/O-heavy engineering changes.",
      "url": "engineering-principles.tar.gz",
      "digest": "sha256:<64-lowercase-hex-characters>"
    }
  ]
}
```

The digest placeholders above are illustrative, not valid final digests.

Each entry must contain:

| Property      | Type   | Rules                                                                                             |
| ------------- | ------ | ------------------------------------------------------------------------------------------------- |
| `name`        | string | 1–64 characters; lowercase alphanumeric and hyphens; no leading, trailing, or consecutive hyphens |
| `type`        | enum   | `skill-md` or `archive`                                                                           |
| `description` | string | 1–1024 characters; purpose and when to use                                                        |
| `url`         | string | Artifact URL, resolved relative to the index URL                                                  |
| `digest`      | string | `sha256:` followed by exactly 64 lowercase hexadecimal characters                                 |

Additional requirements:

- The public index contains only the specification-defined fields.
- No internal source declarations, commit SHAs, or lockfile metadata.
- Sort entries deterministically by name.
- Reject duplicate skill names.
- Preserve upstream skill content without injecting attribution.
- Prefer `skill-md` for standalone `SKILL.md` files.
- Use `archive` for skills with supporting resources.
- Archives must have `SKILL.md` at their root.
- Digests are calculated over exact published artifact bytes.
- All index URLs must resolve correctly under the deployed GitHub Pages project path.

Validate the generated index against the actual v0.2.0 JSON Schema where available. Supplement it with semantic checks for unique names and artifact integrity.

## 4. Source manifest: `skills.config.json`

Keep the existing explicit `external` array.

The manifest expresses desired dependencies, not resolved versions.

Example:

```json
{
  "$schema": "./schemas/skills.config.schema.json",
  "external": [
    {
      "source": "vercel-labs/skills",
      "skill": "find-skills"
    },
    {
      "source": "antfu/ghfs",
      "skill": "ghfs"
    },
    {
      "source": "vercel-labs/agent-skills",
      "skill": "web-design-guidelines",
      "ref": "main"
    },
    {
      "source": "mattpocock/skills",
      "skill": "grill-me",
      "path": "skills/grill-me"
    },
    {
      "site": "https://hugorcd.com",
      "skill": "document-pr"
    }
  ]
}
```

### Configuration schema

Create `schemas/skills.config.schema.json` using JSON Schema Draft 2020-12.

Root object:

- `$schema`: optional string, for editor/tooling schema association.
- `external`: required array of source declarations.
- `additionalProperties: false`.

Each external declaration must match exactly one of two variants.

**GitHub source**

- `source`: required string in `owner/repo` form.
- `skill`: required valid skill name.
- `ref`: optional non-empty Git reference (branch, tag, or commit).
- `path`: optional relative directory inside the repository.
- `as`: optional valid published skill name.
- No unknown properties.

**Website source**

- `site`: required HTTPS URL.
- `skill`: required valid skill name.
- `as`: optional valid published skill name.
- No unknown properties.

Use `oneOf` and `$defs` to express these variants.

Reuse the Agent Skills name constraints:

```json
{
  "type": "string",
  "minLength": 1,
  "maxLength": 64,
  "pattern": "^[a-z0-9]+(?:-[a-z0-9]+)*$"
}
```

Additional semantic validation:

- Reject duplicate dependency identities (`source/site + skill`).
- Reject duplicate effective published names.
- Reject unsafe paths and unsupported source URLs.
- Reject ambiguous skill matches unless `path` is provided.
- Ensure `as` affects only the published name, never which upstream skill is resolved.
- Local skill directories must use the same naming rules.

**Important:** Do not reuse the external discovery `$schema` URI for this file. The manifest is our own format and must reference our own schema.

The manifest should remain easy to edit manually. Do not introduce unnecessary fields such as package versions, authors, repositories, tags, categories, or installation targets.

## 5. Lockfile: `skills.lock.json`

Preserve the existing flat dependency-keyed structure unless there is a concrete compatibility or correctness reason to change it.

The lockfile represents approved immutable resolutions.

Example:

```json
{
  "$schema": "./schemas/skills.lock.schema.json",
  "vercel-labs/skills#find-skills": {
    "commit": "d3701c11b1101251af14c9d148f026e1a47ebe17"
  },
  "antfu/ghfs#ghfs": {
    "commit": "6dce9c1a30a9b3b55beee9c6454df675e9538d6d"
  },
  "https://hugorcd.com#document-pr": {
    "digest": "sha256:<64-lowercase-hex-characters>"
  }
}
```

### Lockfile schema

Create `schemas/skills.lock.schema.json` using JSON Schema Draft 2020-12.

Root:

- `$schema`: optional string.
- Remaining properties: dependency identities.
- Each dependency entry must match exactly one resolution variant.
- No arbitrary entry fields.

**GitHub resolution**

```json
{
  "commit": "<40-lowercase-hex-characters>"
}
```

**Website resolution**

```json
{
  "digest": "sha256:<64-lowercase-hex-characters>"
}
```

Use `oneOf`, `required`, and `additionalProperties: false`.

Validate:

- Commit SHA: `^[a-f0-9]{40}$`
- Digest: `^sha256:[a-f0-9]{64}$`
- Every configured dependency has exactly one lock entry.
- Every lock entry corresponds to a configured dependency.
- Each entry uses the resolution type appropriate for its source.

The `$schema` property must be excluded from dependency iteration.

### Lockfile invariants

- Normal builds never update the lockfile.
- Missing resolutions cause an actionable error.
- Updates are explicit.
- A failed update preserves the previous valid lockfile.
- Unchanged dependencies retain identical entries.
- Removed dependencies disappear on the next successful update.
- Ordering is deterministic.
- No timestamps or environment-specific absolute paths.
- No tokens, credentials, or transient URLs.

### Website reproducibility

A digest alone identifies content but does not guarantee it remains retrievable.

Implement immutable artifact storage for website dependencies without stable revision URLs.

Preferred approach:

```text
vendor/
└── sha256/
    └── <digest-hex>
```

Store the exact approved artifact bytes and verify them against the lockfile before use.

For a v0.2.0 website artifact, retain its original bytes when possible.

For legacy v0.1.0 multi-file sources, package the downloaded files deterministically before recording and storing the resulting artifact digest.

A normal build should consume the approved artifact, not implicitly accept fresh upstream bytes.

GitHub dependencies can be resolved from their pinned commit SHAs; local caching is optional.

Clearly distinguish _reproducible output_ from _offline build capability_. GitHub outages may still prevent building if GitHub sources have not been cached.

## 6. Dependency resolution and state transitions

Implement the following logical lifecycle:

```text
UNRESOLVED
    |
    v
RESOLVED
    |
    v
VERIFIED
    |
    v
STAGED
    |
    v
PUBLISHED
```

Failures terminate the operation without publishing partial output.

These states describe the lifecycle; do not implement an unnecessary state-machine framework.

### Normal build

1. Load and validate configuration.
2. Load and validate lockfile.
3. Verify manifest/lockfile consistency.
4. Resolve local skills and approved external dependencies.
5. Verify source revisions and content digests.
6. Generate deterministic artifacts in a staging directory.
7. Generate the discovery index.
8. Validate all references and hashes.
9. Replace local output after successful validation.
10. Preserve the lockfile unchanged.

### Dependency update

1. Load the existing manifest and lockfile.
2. Resolve current upstream dependency revisions.
3. Download and verify changed content.
4. Prepare new vendor artifacts where necessary.
5. Generate a complete candidate lockfile.
6. Validate the candidate against the manifest.
7. Verify a complete build using the candidate.
8. Commit the new lockfile and required vendor artifacts only after validation.

Never modify the approved lockfile incrementally during resolution.

### Retry behavior

- Retries apply only to transient network failures.
- Maximum three attempts by default.
- Bounded exponential backoff with jitter.
- No retries for schema errors, invalid revisions, missing skills, or integrity failures.
- Git operations must have bounded execution time.
- Temporary directories must be cleaned up after both successful and failed operations.

Prefer sequential resolution unless measured performance warrants bounded concurrency.

## 7. GitHub source resolution

Use Git rather than implementing a GitHub API client.

For each GitHub dependency:

1. Resolve repository and optional `ref`.
2. During updates, resolve the selected revision to a full commit SHA.
3. During normal builds, use the locked commit SHA.
4. Locate the skill using an explicit path or `SKILL.md` frontmatter name.
5. Reject missing or ambiguous matches.
6. Validate metadata and supporting files.
7. Package or publish the artifact.
8. Verify its digest.

Do not silently fall back from a locked commit to a newer branch head.

Ensure Git operations cannot prompt interactively for credentials.

Prevent repository-local Git configuration, hooks, or submodule behavior from unexpectedly executing untrusted code during source resolution.

Do not execute scripts bundled in retrieved skills.

## 8. Website source resolution

Support Agent Skills Discovery v0.2.0 and the legacy v0.1.0 format where needed for existing sources.

For a website declaration:

```json
{
  "site": "https://hugorcd.com",
  "skill": "document-pr"
}
```

Resolve the discovery index using the supported well-known paths:

```text
/.well-known/agent-skills/index.json
/.well-known/skills/index.json
```

Prefer v0.2.0.

### v0.2.0 behavior

- Validate `$schema` and each entry.
- Resolve artifact URLs against the upstream index URL using standard URL resolution rules.
- Download the artifact with timeout and size limits.
- Verify its SHA-256 digest.
- Validate the artifact type and archive structure.
- Preserve verified artifact bytes.
- Reject unsupported or malformed inputs.

### Legacy v0.1.0 behavior

- Validate the legacy file list.
- Download each declared file safely.
- Ensure required `SKILL.md` exists.
- Reject unsafe paths and malformed metadata.
- Produce a deterministic archive where multiple files exist.
- Compute the digest of the resulting distribution artifact.

### Security

- HTTPS only for remote website sources.
- No arbitrary code execution.
- URL protocols and redirect destinations validated.
- Bounded download sizes and response times.
- No absolute paths or `..` traversal.
- No unsafe symlink or hard-link extraction.
- Bounded decompressed archive size.
- Actionable errors for unsupported formats.

Do not invent additional supported source protocols without actual demand.

## 9. Artifact generation and determinism

Keep the current approach of generating either:

```text
<skill>/SKILL.md
```

or:

```text
<skill>.tar.gz
```

For archive generation:

- Sort files deterministically.
- Normalize timestamps, user IDs, group IDs, and ownership metadata.
- Preserve appropriate executable bits.
- Use stable compression settings.
- Normalize platform-dependent gzip metadata.
- Keep the archive root layout required by the discovery specification.
- Never include `.git`, `node_modules`, temporary files, or host-specific artifacts.

Calculate the digest from the final bytes that will actually be published.

Test identical builds across repeated executions.

Do not hardcode the GitHub Pages hostname into every artifact URL.

### Pages workflow

Use the official GitHub Pages Actions.

Suggested `.github/workflows/pages.yml`:

```yaml
name: Deploy Skills

on:
  push:
    branches: [main]
    paths:
      - "skills/**"
      - "lib/skills/**"
      - "schemas/**"
      - "vendor/**"
      - "tests/skills/**"
      - "skills.config.json"
      - "skills.lock.json"
      - "package.json"
      - "bun.lock"
      - "tsconfig.json"
      - ".github/workflows/pages.yml"
  workflow_dispatch:

concurrency:
  group: github-pages
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: "1.4.4"

      - run: bun install --frozen-lockfile
      - run: bun run typecheck
      - run: bun test
      - run: bun run build
      - run: bun run skills:verify

      - uses: actions/upload-pages-artifact@v4
        with:
          path: dist
          include-hidden-files: true

  deploy:
    needs: build
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

This is a reference workflow. Verify the relevant action versions and pin to immutable action SHAs where appropriate.

The `skills:verify` command is a required v2 implementation task, not an existing assumed command.

The workflow must:

1. Install dependencies reproducibly.
2. Typecheck.
3. Run tests.
4. Build the complete skills distribution from approved dependencies.
5. Verify the generated index, URLs, and digests.
6. Upload the complete `dist/` directory.
7. Deploy only after a successful build.
8. Preserve the previous successful Pages deployment if the current job fails.

Use `include-hidden-files: true` to preserve `.well-known/`. Avoid manually constructing Pages artifacts unless the official action demonstrably fails.

Add `.nojekyll` to the generated site root.

Use the normal GitHub Pages environment and minimal permissions.

### HTTP compatibility

Verify deployed responses:

| Resource     | Expected content type           |
| ------------ | ------------------------------- |
| `index.json` | `application/json`              |
| `SKILL.md`   | `text/markdown` or `text/plain` |
| `.tar.gz`    | `application/gzip`              |

GitHub Pages controls HTTP headers; do not assume custom headers can be configured in this project.

Verify GET and HEAD requests, redirects, status codes, and digest integrity.

## 11. Automated dependency updates

Keep a separate `.github/workflows/update-skills.yml`.

Run daily and allow manual dispatch.

The workflow must:

1. Check out the repository.
2. Install pinned tooling.
3. Run dependency resolution in update mode.
4. Prepare changed lockfile and vendor artifacts.
5. Run typechecking, tests, a complete candidate build, and artifact verification.
6. Generate a concise update summary.
7. Create or update one pull request containing only relevant changed files.

The PR should show:

- Added, removed, and updated skills.
- Old and new commit SHAs or digests.
- Links to GitHub source diffs where possible.
- Newly introduced or modified executable scripts.
- Any significant source or metadata changes.
- Verification results.

Avoid creating PRs when there are no changes.

Do not automatically merge dependency updates.

The workflow must not publish unreviewed upstream updates to GitHub Pages.

Use standard GitHub Actions and `peter-evans/create-pull-request`, or another established equivalent. Avoid custom GitHub API automation.

## 12. CLI and package scripts

Use Bun as the development runtime.

Provide predictable package scripts:

```json
{
  "scripts": {
    "build": "bun lib/skills/index.ts build",
    "skills:resolve": "bun lib/skills/index.ts resolve",
    "skills:update": "bun lib/skills/index.ts update",
    "skills:verify": "bun lib/skills/index.ts verify",
    "typecheck": "tsc --noEmit",
    "test": "bun test"
  }

```

These are suggested commands, not a requirement to implement a complex command framework.

Expected semantics:

| Command          | Behavior                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| `build`          | Generate complete distribution from locked inputs                                                       |
| `skills:resolve` | Resolve missing dependencies explicitly; fail rather than silently update existing approved resolutions |
| `skills:update`  | Generate candidate updated resolutions and required vendor artifacts                                    |
| `skills:verify`  | Verify published output structure, index, URLs, and hashes                                              |
| `test`           | Run automated tests                                                                                     |
| `typecheck`      | Static TypeScript validation                                                                            |

Avoid redundant aliases or overlapping commands.

The CLI should return nonzero exit codes on failure and provide concise, actionable diagnostics.

## 13. Atomicity and filesystem behavior

Build into a temporary staging directory.

Do not remove the previously valid `dist/` before the new build succeeds.

After validation, use an appropriate atomic or recoverable replacement strategy.

Consider platform-specific rename semantics; do not assume POSIX directory replacement works identically on Windows.

Treat filesystem operations as side effects at the boundary.

Important invariants:

- Failed builds retain previous valid output.
- Failed dependency updates retain previous approved lockfile state.
- Temporary directories are always cleaned up.
- Repeated builds do not change lockfile content.
- Repeated builds with identical inputs produce identical artifact bytes.
- No shared mutable output directories are written concurrently without coordination.

Do not claim atomicity for a multi-file update unless the implementation provides a real recovery strategy.

## 18. Engineering principles and review

Before implementing, review the plan against `skills/engineering-principles/SKILL.md`.

Focus on:

**State transitions:** The build and update lifecycle, including invalid transitions and incomplete operations.

**Invariants:** Lockfile consistency, approved dependency versions, unique names, verified artifacts, and successful-only publication.

**Idempotency:** Repeated builds and updates must not cause unexpected changes.

**Failure recovery:** Network outages, malformed sources, interrupted updates, and partial filesystem writes.

**Concurrency:** CI job overlap, shared output directories, and dependency update races.

**Boundaries:** Separate parsing, validation, resolution, artifact generation, and filesystem/network I/O.

**Observability:** Failures must identify the source, operation, and required remediation.

Avoid implementing runtime abstractions for each principle. Apply the principles to simplify the design and prevent actual defects.
